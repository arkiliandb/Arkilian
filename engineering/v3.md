## v3 Core Principles

1. **Single source of truth per account** — never two writers for the same balance
2. **Durability before ack** — write is not "done" until it's on disk on 2 of 3 nodes
3. **Serializable isolation** — SQLite already gives us this, we keep it
4. **No background merge** — ever. If it can't be replayed deterministically, we don't do it

## Architecture: Sharded Raft over SQLite

Forget N full copies. We build **shards, each is a 3-node Raft group**.

```
Client → Router → Shard (leader) → Raft log → 2 followers → ack
                     ↓
                  SQLite (WAL, fsync)
```

- **Shard key:** `account_id` (or `user_id`). Consistent hash: `shard = hash(id) % 1024`. Start with 16 shards, grow to 1024.
- **Each shard:** 3 nodes (leader + 2 followers) in different AZs. Leader handles all writes for that shard. Followers serve stale reads.
- **Our ring buffer becomes the Raft log:** instead of async POST to one server, we POST to 2 followers and wait for 200. That's our durability guarantee.

### Why this works for Arkilian users

- **No double-spend:** one leader per account means SQLite's row lock is the global lock
- **No data loss:** fsync on leader + 1 follower before we return to the app. If leader dies, follower has the WAL.
- **Strong reads:** `SELECT balance` goes to leader (or follower with `?consistency=linearizable` which waits for leader heartbeat)
- **Fast reads:** `SELECT transaction history` goes to any follower — 120k reads/sec per node from our bench

## Write Path (the critical part)

1. App calls `db_exec("UPDATE accounts SET balance = balance - 100 WHERE id = ?")`
2. Router hashes id → shard 7 → sends to leader
3. Leader:
   - acquires our existing write mutex
   - appends to local WAL, fsync
   - POSTs the WAL frame to followers (our ring buffer, but synchronous)
   - waits for 1 follower ack (2 of 3 total)
   - commits in SQLite, returns to client
4. Latency: ~8-12ms intra-region (vs our current 64µs local). That's the price of Arkilian users-grade.

## Read Path

- **Read-our-writes:** router pins the user's session to the leader for 5 seconds after a write. No bloom filter needed — just a cookie with `shard_id`.
- **Point queries:** 70k/sec per node (our bench) × 3 nodes × 16 shards = 3.3M reads/sec
- **Analytics:** followers serve stale reads with `max_staleness=1s`

## What we keep from v1

- SQLite with WAL + synchronous=NORMAL (but we fsync manually in Raft)
- Our mutex and ring buffer — just make the POST synchronous and wait for quorum
- The 9 MB memory footprint per node
- All 83 tests — they still pass, we just run them on 3 nodes

## What we throw away from the N-copy idea

- No background merge — Raft applies logs in order on all nodes
- No bloom filters for routing — consistent hash is deterministic
- No eventual consistency — every read is either linearizable or bounded-stale

## Tech stack for v2

- **Consensus:** HashiCorp raft (Go) — battle-tested, we embed it, no need to write Raft
- **Storage:** our C library unchanged, just called by the Go leader
- **Network:** gRPC between nodes (not HTTP POST) for the WAL frames — lower latency
- **Deployment:** Fly.io 3-node clusters per shard, Johannesburg/London/Frankfurt for Arkilian users latency

2. Build one 3-node shard for Arkilian users

4. When it passes, shard by account_id
